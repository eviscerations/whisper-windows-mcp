Поточна версія: **v2.5.0**

## Принципи проєктування

Ці принципи визначають кожне рішення в цьому проєкті і мають пріоритет над швидкістю додавання функцій.

**Мінімізація використання Claude API.** Весь робочий процес транскрипції — сканування, аналіз, черга, виконання, перевірка, перемикання моделей — має виконуватися з мінімальною кількістю взаємодій з Claude. Цей інструмент має повноцінно працювати для користувачів безкоштовного плану Claude, які не платять за підписки Pro або Max. Кожен виклик інструменту витрачає ліміт використання. Проєктуйте відповідно.

**Завжди лише один екземпляр whisper.** Ніколи не запускайте другий процес whisper-cli.exe, поки один вже виконується. Блокування процесу є обов'язковим і не підлягає переговорам.

**Локальний пріоритет, приватно за замовчуванням.** Аудіо ніколи не покидає комп'ютер. Для основних функцій хмарні API не потрібні. Необов'язкові інтеграції (наприклад, завантаження моделей з Hugging Face) мають бути чітко задокументовані як необов'язкові.

**Явний контроль користувача.** Жодних тихих масових операцій. Руйнівні або незворотні дії потребують підтвердження. Користувач завжди має знати, що відбуватиметься, до того, як це станеться.

**Unicode-безпечні шляхи.** Весь файловий введення-виведення має правильно обробляти не-ASCII імена файлів, включно з українськими, японськими, китайськими, емодзі, дужками та іншими спеціальними символами.

**Модульність і компонованість.** Інструменти незалежні. Користувачі використовують те, що їм потрібно. Жодна функція не повинна вимагати іншої, якщо цього неможливо уникнути.

**Оптимізація перед функціями.** Якщо сумніваєтеся між додаванням функції та зменшенням навантаження на систему або кількості викликів API — зменшуйте навантаження. Великі оптимізаційні роботи дорого коштують. Спроєктуйте архітектуру правильно з першого разу.

**Автопросування пакету (критичне виправлення помилки):** `start_batch` раніше вимагав активного опитування для просування черги. Коли процес завершується, пакет самостійно просувається через зворотній виклик виходу з нульовими витратами на опитування і нульовим споживанням API. - Змінна середовища `WHISPER_PRIVACY_MODE` — при значенні `true` всі відповіді інструментів повертають лише метадані (ім'я файлу, кількість слів, шлях збереження). Жоден текст транскрипції не передається API Claude за жодних обставин. Транскрипції існують лише як локальні файли.

- Ворота режиму конфіденційності (`checkPrivacyGate()`) — спрацьовують перед кожною операцією, коли ефективний режим конфіденційності активний.

## Заплановано — v2.5.0: Постійний сервер моделі

Тримати модель Whisper резидентною між транскрипціями замість її перезавантаження при кожному виклику.

Це найбільше доступне підвищення пропускної здатності. whisper-cli є одноразовим: він перезавантажує повну модель при кожному виклику, і v2.4.0 виміряла це перезавантаження як ~110 с на GPU з обмеженою пам'яттю — фіксований податок, що сплачується за файл, незалежно від тривалості аудіо. Для пакетних і архівних навантажень воно домінує над часом виконання більше, ніж сама транскрипція.

**Підхід:** запустити вбудований `whisper-server` (HTTP) від whisper.cpp як єдиний довготривалий процес з моделлю, що тримається в пам'яті. MCP-сервер надсилає кожну транскрипцію до нього через localhost і отримує результати без повторної сплати вартості перезавантаження.

**Узгодження з «завжди лише один екземпляр whisper»:** принцип збережено, механізм еволюціонує. Резидентний сервер *стає* єдиним екземпляром; блокування процесу змінюється з «ніколи не запускати другий whisper-cli» на «серіалізувати запити до одного резидентного сервера». Жодної конкурентності не вводиться.

**Обмеження проєктування:**
- Явний життєвий цикл: start / stop / status із перевіркою стану. Сервер ніколи не запускається тихо як побічний ефект стороннього виклику.
- Прив'язка лише до localhost — ніколи до маршрутизованого інтерфейсу. Жодного відкриття в мережу (узгоджено з принципом локального пріоритету і посиленням v2.4.0).
- М'яке відкочування: якщо сервер не запущено, транскрипція все одно працює через існуючий одноразовий шлях whisper-cli. Сервер є оптимізацією, а не жорсткою залежністю.
- `switch_model` перезавантажує модель у резидентному сервері (усе одно значно дешевше в перерахунку, ніж перезавантаження на файл).
- Ворота конфіденційності і згоди незмінні — вони знаходяться над механізмом транскрипції.
- Вибір порту з обробкою колізій; чисте вимкнення за SIGINT/SIGTERM разом із існуючим очищенням тимчасових файлів.

**Статус — Фаза 1 ✅ реалізовано (очікує релізу):** інструмент `whisper_server` (`start` / `stop` / `status`); блокувальні `transcribe_audio` і `transcribe_batch` маршрутизуються через резидентний сервер по localhost (`127.0.0.1`, перевірено за поточним HTTP API `whisper-server` від whisper.cpp); `switch_model` гаряче замінює резидентну модель через `POST /load` без перезапуску; захист тайм-ауту переднього плану пропускається в режимі сервера (немає перезавантаження, за яке платити); `check_config` повідомляє стан сервера; власний сервер завершується при вимкненні для звільнення VRAM. Правило один-рушій / спільний-VRAM забезпечується жорстким запобіжником у шляху відокремленого запуску плюс дружніми відмовами: поки сервер працює, фонові завдання, `start_batch`, `generate_subtitles`, вивід `lrc`/`csv` і параметри для окремого запиту, які HTTP API не підтримує (`beam_size`, `best_of`, `word_timestamps`, `diarize`, `tinydiarize`, `vad_model`, `offset_t`, `duration` тощо), відхиляються з повідомленням «спочатку зупиніть сервер» замість тихої деградації. Конфігурація: `WHISPER_SERVER_PATH`, `WHISPER_SERVER_PORT` (типово 8571, лише localhost).

**Статус — Фаза 2 (заплановано):** маршрутизувати фонові / `start_batch` через резидентний сервер. Це більший виграш для архіву/пропускної здатності, і він потребує переробки шару завдань/черги навколо HTTP-запитів замість відокремлених PID (прогрес без PID, скасування). Переоцінити після завершення Фази 1.

## Заплановано — v2.6.0: TinyDiarize (моно-зміни доповідача, нуль додаткових залежностей)

Підтримка `--tinydiarize` з варіантами моделей, що підтримують `tdrz` (наприклад `ggml-small.en-tdrz.bin`). На відміну від стерео-прапорця `--diarize` (v2.2.0), TinyDiarize позначає зміни доповідача на **моно** записах і не потребує нічого, крім файлу моделі — ні Python, ні зовнішнього сервісу.

**Обсяг:**
- Додати варіант(и) моделі `tdrz` до `MODEL_REGISTRY`, щоб `download_model` міг завантажувати їх з існуючих довірених просторів імен Hugging Face.
- Провести параметр `tinydiarize` через `buildArgs` і `spawnDetached`, щоб він працював у блокувальному, фоновому і пакетному режимах.

**Статус:** ✅ Реалізовано (очікує релізу) — параметр `tinydiarize` у `transcribe_audio` і `generate_subtitles` (працює в блокувальному і фоновому режимах), `--tinydiarize` проведено через обидва конструктори аргументів, а `small.en-tdrz` додано до `MODEL_REGISTRY` для `download_model`. Відповідає ethos: локальний пріоритет, нуль додаткових залежностей.

## Пізніше / На розгляді

Не заплановано, але відповідає ethos і переглядається в міру наявності ресурсів.

### Міграція на Bun
Перенести середовище виконання з Node.js на [Bun](https://bun.sh), щоб скоротити час холодного старту MCP-сервера і прибрати крок збірки `tsc` (вихідний код запускається безпосередньо). Знижено з колишнього слоту v2.5.0: оскільки реальним вузьким місцем є вартість перезавантаження моделі при кожному виклику (див. v2.5.0 вище), скорочення часу запуску Node є маргінальним виграшем, а зрілість Bun на Windows плюс зміна моделі розповсюдження несуть ризик. Варто зробити зрештою як необов'язкову оптимізацію, а не пріоритет.

### Робочий процес перейменування і зіставлення відеопроєкту
Важча половина інструментарію проєкту, щойно завершиться пошук транскрипцій по всьому проєкту (v2.7.0): нечітке зіставлення транскрипцій відредагованих кліпів з вихідними транскрипціями для визначення точок походження і відображення описових імен файлів, запропонованих Claude.

**Обмеження проєктування:**
- Вихідні файли **ніколи не перейменовуються і не змінюються**
- Усі перейменування вимагають **явного підтвердження користувача**
- Аналіз і зіставлення відбуваються локально — Claude викликається лише коли користувач переглядає результати, мінімізуючи виклики API

**Статус:** Фаза проєктування.

### Очищення транскрипції на основі правил
Локальна детермінована постобробка — видалення слів-заповнювачів і невдалих початків, під контролем користувача. Найцінніше для користувачів режиму конфіденційності, де транскрипція ніколи не досягає Claude для очищення. Навмисно вузьке: розбиття на абзаци і сегментація за темами — це те, що Claude уже добре робить над поверненим текстом, а експорт у PDF/DOCX — це розповзання обсягу в генерацію документів — обидва поза межами охоплення тут.

**Статус:** На розгляді.

### Розрізнення доповідачів (pyannote-audio)
Повне розрізнення доповідачів у моно з мітками ID доповідача по всьому запису. Відрізняється від вбудованого стерео-прапорця `--diarize` (v2.2.0) і TinyDiarize (v2.6.0).

**Реалізація:** потребує [pyannote-audio](https://github.com/pyannote/pyannote-audio) — бібліотеки на Python з вимогою токена доступу до Hugging Face, повністю окремий стек залежностей. Знижено в пріоритеті: це суперечить ethos локального пріоритету / нульових залежностей, а TinyDiarize уже покриває моно-випадок без залежностей. Якщо буде реалізовано, постачатиметься як необов'язковий розширений додаток із власною документацією з налаштування, ніколи в основному пакеті.

**Статус:** Знижено в пріоритеті / необов'язково.

### Переклад на не-англійські мови
Прапорець `--translate` Whisper орієнтований лише на англійську. Довільні цільові мови потребують зовнішнього API перекладу або локальної моделі перекладу.

**Варіанти, що розглядаються:** LibreTranslate (можна розгорнути самостійно, локальний пріоритет), локальний LLM-переклад або явна документація поза межами охоплення.

**Статус:** Відкладено, очікує рішення щодо локального пріоритету проти залежності від API.

## Поза межами охоплення / Не заплановано

Функції, навмисно виключені, зафіксовані тут, щоб рішення було явним і не поставало знову і знову.

### Живе транскрибування з мікрофона — не заплановано
Транскрибування в реальному часі з живого мікрофона раніше було заплановано на v2.7.0. Вирізано, оскільки воно суперечить основному дизайну проєкту:
- **Невідповідність архітектури:** MCP є запит/відповідь, а не потоковим. Живе захоплення потребувало б або безперервного опитування (спалює бюджет API), або довгого блокувального виклику, що впирається в захист тайм-ауту переднього плану v2.4.0.
- **Принципи один-екземпляр / мінімізації API:** повернення поточних сегментів до Claude — це постійне бомбардування викликами інструментів — протилежність «функціональності для користувачів безкоштовного плану» — а довготривалий потоковий процес навантажує блокування процесу.
- **Зовнішня залежність:** воно залежало б від стабільного потокового API у whisper.cpp, який не в нашому розкладі.

Живі субтитри — це окрема категорія продукту (низька затримка, управління пристроями, VAD), відмінна від інструмента файлової/пакетної транскрипції. Користувачам, яким це потрібно, краще підійде спеціалізований інструмент реального часу.

### Транскрипція URL YouTube (yt-dlp) — не заплановано як вбудований інструмент
Пряме перетворення YouTube на транскрипцію через yt-dlp раніше планувалося. Відкинуто як першокласну функцію, оскільки:
- **Поверхня безпеки:** воно додає завантаження довільних URL і виклик підпроцесу з вводом, керованим користувачем, скасовуючи посилення v2.4.0, яке зменшило саме цю поверхню.
- **Обслуговування:** yt-dlp часто ламається, коли YouTube змінюється — постійне зобов'язання з обслуговування.
- **Локальний пріоритет і ліцензування:** отримання мережевого контенту знаходиться поза межами локального пріоритету, а вбудовування завантажувача в проєкт із комерційною ліцензією — це сіра зона ToS/відповідальності.
- **Надлишковість:** користувачі можуть запустити yt-dlp самостійно і спрямувати `transcribe_audio` на отриманий файл.

**Альтернатива:** задокументовано як рецепт (запустіть yt-dlp, потім транскрибуйте файл) у README / TROUBLESHOOTING, а не як підтримуваний інструмент — робочий процес залишається доступним без володіння залежністю чи поверхнею атаки.
